# Red-team review: scope & complexity critic + contract verifier

Scope: plan.md + phase-01..08, checked against docs/game-rules.md, docs/tech-stack.md,

## Finding 1: `room_sessions.closed_at` is defined, queried, and exposed via API, but no phase ever writes it

- **Severity:** Critical
- **Location:** Phase 4, section "D1 schema", `phase-04-worker-auth-and-d1.md:57` (column def), `:88` (`GET /api/sessions` → `open` field), `:90` (`GET /api/rooms/:code` → `closed` field), `:94-97` (query selects `r.closed_at`); Phase 5, section "Requirements", `phase-05-room-durable-object-realtime.md:28` ("an empty room closes")
- **Flaw:** The schema comment says `closed_at` is `NULL while the room is open` and two REST contracts (`closed`, `open`) are built on it, but the only phase that owns room lifecycle (phase 5, `apps/worker/src/room-do*.ts`) never issues a D1 write to `room_sessions`. Its D1 access is limited to `env.DB.batch(insert hand_results per seat)` at hand end (`phase-05-room-durable-object-realtime.md:122`) and a read of `room_sessions` at WS-upgrade time (`phase-05-room-durable-object-realtime.md:83`). Nothing sets `closed_at` when "an empty room closes."
- **Failure scenario:** Every room reports `closed: false` / `open: true` forever. Wireframe 02's "Ván gần đây" column explicitly branches on this: `docs/wireframe/02-lobby.html:102` — "Phiên đang mở có nút 'Vào lại'" (an open session shows a "Vào lại"/rejoin button). Every historical room, including ones that ended weeks ago, will show a rejoin button that leads to a 404 or a dead room, and `GET /api/rooms/:code` will never report a room as closed to a client checking before join.
- **Evidence:**
  - `phase-04-worker-auth-and-d1.md:57`: `closed_at    INTEGER    -- NULL while the room is open`
  - `phase-04-worker-auth-and-d1.md:88`: `GET /api/sessions | ... | { sessions: [{ ..., open }] }`
  - `phase-05-room-durable-object-realtime.md:28`: "A departing host passes the crown to the next seat; an empty room closes."
  - No `UPDATE room_sessions` appears anywhere in phase-04 or phase-05 (grep-verified).
- **Suggested fix:** Either (a) add an explicit step to phase 5 — when the last seat leaves/disconnects-permanently, `ctx.waitUntil` an `UPDATE room_sessions SET closed_at = ? WHERE code = ?` — and list it in phase 5's Implementation Steps and Related Code Files, or (b) if "closes" only ever means the DO going idle (not a real lifecycle event worth persisting), drop the column, the `closed`/`open` API fields, and the associated wireframe copy from scope, and have the lobby always show "Vào lại" for any past room instead of pretending to track open/closed state.

## Finding 2: `HandResult.nextLeadSeat` is typed as `number` (non-nullable) but has no defined value on a Báo Sâm failure, where `RulesState.winnerSeat` is `null`

- **Severity:** High
- **Location:** Phase 3, section "Báo sâm window", `phase-03-rules-engine-game-state-and-settlement.md:81` (`samResult = 'fail'`, `winnerSeat = null`); Phase 5, section "WebSocket message types", `phase-05-room-durable-object-realtime.md:66` (`nextLeadSeat: number`) and `phase-05-room-durable-object-realtime.md:109` (`beginHand()` passing `lastWinnerSeat`)
- **Flaw:** The only rule-engine path that ends a hand with `winnerSeat === null` is a failed Báo Sâm (`phase-03-rules-engine-game-state-and-settlement.md:81`: "hand ends immediately when a declarer's play is beaten ... `winnerSeat = null`"). Phase 5's `beginHand()` computes the next hand's leader as `handNo === 0 ? undefined : lastWinnerSeat` (`phase-05-room-durable-object-realtime.md:109`), and `HandResult.nextLeadSeat` is a required `number` field consumed verbatim by the UI ("Centre text names the next leader from `result.nextLeadSeat`", `phase-07-web-game-table-and-results.md:159`, and wireframe 05's "Tuấn cầm cái ván sau" line). Neither `docs/game-rules.md` nor phase 3's "Next Steps" (which only flags đền bài wording and chặt chồng stacking, `phase-03-rules-engine-game-state-and-settlement.md:197-200`) says who leads the hand after a failed Báo Sâm.
- **Failure scenario:** `RoomDO.endHand()` / `buildHandResult()` has to invent a value for `nextLeadSeat` (declarer? seat 0? the previous leader again?) that no spec, test matrix, or phase file defines, and `beginHand()`'s `lastWinnerSeat` variable is `null` going into `createHand`, which is typed to accept `leadSeat?: number` (`phase-03-rules-engine-game-state-and-settlement.md:65`) — a `null` passed where `undefined`/`number` is expected either throws under `strict` TypeScript or silently falls back to the lowest-card rule, which is a rule invented mid-implementation, not confirmed by the group.
- **Evidence:** `phase-03-rules-engine-game-state-and-settlement.md:81` `winnerSeat = null`; `phase-05-room-durable-object-realtime.md:66` `nextLeadSeat: number`; `phase-05-room-durable-object-realtime.md:109` `handNo === 0 ? undefined : lastWinnerSeat`.
- **Suggested fix:** Add this as a third flagged rule reading in phase 3 (next to đền bài and chặt chồng) — e.g., "on Báo Sâm failure, the seat to the declarer's left leads next" — write it into `docs/game-rules.md`, and make `settle`/`createHand`'s contract explicit about what seat feeds `nextLeadSeat` in this case, rather than leaving it to be discovered while wiring phase 5.

## Finding 3: The approved wireframe's "Rời phòng" (leave room) button has no implementation step in phase 6, though the store method it needs already exists

- **Severity:** High
- **Location:** Phase 6, section "Implementation Steps" step 7, `phase-06-web-shell-login-lobby-waiting.md:144-155`; wireframe `docs/wireframe/03-room-waiting.html:70` (`<button class="btn btn-d">Rời phòng</button>`) and its annotation `docs/wireframe/03-room-waiting.html:92`; `docs/design-guidelines.md:65` ("Danger: ... Used for 'Rời phòng', confirm dialogs.")
- **Flaw:** Phase 6's `room.svelte.ts` architecture already declares a `leave()` wrapper (`phase-06-web-shell-login-lobby-waiting.md:89`: "thin `ready()/start()/updateSettings()/leave()` wrappers"), and the DO already handles a `leave` message type (`phase-05-room-durable-object-realtime.md:55` `ClientMsg` union includes `'leave'`, and `phase-05-room-durable-object-realtime.md:98` "leave -> drop the seat..., reassign host"). But step 7's description of `waiting-screen.svelte` (`phase-06-web-shell-login-lobby-waiting.md:144-155`) only lists: room code/share/copy, settings chips, seat list, and the host `Bắt đầu` / player `Sẵn sàng` toggle at "bottom of the left column." It never mentions rendering the `Rời phòng` button, which the wireframe places in that exact same left-column footer (`.foot` block, `docs/wireframe/03-room-waiting.html:66-71`) alongside `Bắt đầu`.
- **Failure scenario:** Success criterion "pixel-faithful to the wireframes" (`phase-06-web-shell-login-lobby-waiting.md:18`) fails a visual/functional diff; players have no way to leave a room from the waiting screen without closing the tab, which also means the host-crown-transfer path (`phase-05-room-durable-object-realtime.md:28`) is never exercised outside of an unclean disconnect, undermining phase 8's smoke-test item 9 ("Host leaves the waiting room; the crown moves to the next seat" — `phase-08-deploy-docs-and-smoke-test.md:92`), which has no UI trigger to test with.
- **Evidence:** `docs/wireframe/03-room-waiting.html:70` `<button class="btn btn-d">Rời phòng</button>`; `docs/design-guidelines.md:65` names it explicitly as the danger-button use case; absent from `phase-06-web-shell-login-lobby-waiting.md:144-155` and from the "Related Code Files" list at `phase-06-web-shell-login-lobby-waiting.md:98-114`.
- **Suggested fix:** Add one bullet to step 7: render a `.btn-d` "Rời phòng" button under `Bắt đầu`/`Sẵn sàng` that calls `room.leave()` then `go('#/lobby')`, matching the wireframe's `.foot` layout. No new component or file needed — this is a one-line gap in an existing step, not new scope.

## Finding 4: Two independently-maintained sums of the same value ("net lá") with no reconciliation path

- **Severity:** Medium
- **Location:** Phase 5, section "Hand lifecycle and alarm scheduling", `phase-05-room-durable-object-realtime.md:119-122` (`endHand()`); Phase 4, section "Route contracts", `phase-04-worker-auth-and-d1.md:92-97` (`GET /api/sessions` query)
- **Flaw:** `endHand()` updates `seats.total_la` in DO storage (live, authoritative for in-game display) and separately `ctx.waitUntil`s a D1 batch insert into `hand_results` (history, used by `GET /api/sessions`'s `SUM(h.delta_la) AS net_la`). These are two independent write paths computing what should be the same running total, and the risk table itself concedes the D1 write can fail silently: "`env.DB` write at hand end fails and blocks the snapshot... `ctx.waitUntil` the D1 batch — `seats.total_la` is authoritative for live play and D1 is history only" (`phase-05-room-durable-object-realtime.md:181`). Phase 8 explicitly rules out monitoring ("What is NOT in this phase: CI, staging environment, monitoring, backups", `phase-08-deploy-docs-and-smoke-test.md:45`).
- **Failure scenario:** A dropped `waitUntil` write (D1 429, transient network error, Worker eviction before the promise resolves) leaves `hand_results` missing rows for a hand. `seats.total_la` (live, correct) and the lobby's historical "Tổng" chip / recent-sessions net score (computed from `hand_results`, now wrong) permanently diverge for that room with nothing to detect or repair it — there is no reconciliation job, and per Finding 1's `closed_at` gap, there's also no way to know the room ever closed.
- **Evidence:** `phase-05-room-durable-object-realtime.md:119-122`, `:181`; `phase-04-worker-auth-and-d1.md:92-97`.
- **Suggested fix:** Either accept the risk explicitly in `docs/tech-stack.md` (state that lobby history is best-effort and can drift from live totals — a legitimate YAGNI call for a ≤20-person private app), or replace `ctx.waitUntil` with a retried write recorded in the `room` DO row (e.g., a small outbox flag) so a later action can resend a failed batch. Do not add this as new scope silently discovered by whoever implements phase 5 — decide now, since it changes phase 5's file list either way.

## Finding 5: `reducer-events.ts` is a named fallback file in the risk table that phase 3's own "Related Code Files" contract never lists

- **Severity:** Medium
- **Location:** Phase 3, section "Risk Assessment", `phase-03-rules-engine-game-state-and-settlement.md:186`; section "Related Code Files", `phase-03-rules-engine-game-state-and-settlement.md:143-147`
- **Flaw:** The risk table's mitigation for "a reducer file creeps past 200 lines" is "the step-2 helper split keeps files small, with `reducer-events.ts` as the overflow" — introducing a fifth source file by name. But "Related Code Files → Create" for this phase lists exactly four: `state.ts`, `reducer-play.ts`, `reducer-sam.ts`, `settle.ts` (plus tests). `reducer-events.ts` is not declared as creatable there, is not in phase 3's "Implementation Steps," and is not mentioned as an export surface in step 1's `index.ts` update.
- **Failure scenario:** If a phase-3 implementer actually needs the overflow file, the plan's own file inventory becomes wrong the moment they create it (Success Criteria checks "every file in `packages/rules/src` ≤200 lines" but nothing checks the file list matches Related Code Files), and phase 5/7, which only import from `@samloc/rules`'s public surface, are unaffected — but the plan's stated file-ownership contract for phase 3 (`plan.md:63`: "Owns `packages/rules/src/{state,reducer-*,settle}.ts`") technically still covers a `reducer-*.ts` file, so this is contained, just inconsistent bookkeeping.
- **Evidence:** `phase-03-rules-engine-game-state-and-settlement.md:143-147` vs `:186`.
- **Suggested fix:** Either remove the `reducer-events.ts` mention from the risk table (rely on the `reducer-*` glob ownership in `plan.md:63` to cover it implicitly) or add it to "Related Code Files → Create" now so the file inventory is self-consistent.

## Finding 6: `table-screen.svelte` (phase 7) has no planned logic-extraction module, unlike phase 5's DO which splits the same kind of complexity into separate files

- **Severity:** Medium
- **Location:** Phase 7, section "Local state in `table-screen.svelte`", `phase-07-web-game-table-and-results.md:56-66`; section "Component tree", `phase-07-web-game-table-and-results.md:42-54`; contrast with Phase 5, `phase-05-room-durable-object-realtime.md:131-135` ("Related Code Files")
- **Flaw:** `table-screen.svelte` alone is specified to own: the room-store connection, a `selected` card-id array, a `tags` queue array, a 250 ms `now` ticker (only while it's someone's turn), three `$derived` values (`combo`, `canPlay`, `remain`), the `transform: scale(tableScale)` wrapper, an `$effect` that clears `selected` on every snapshot, and orchestration of 9 child components including a variable-length `opponent-seat` list and the tag-queue lifecycle described in step 10 ("push on `onEvent`, drop after 1.6 s", `phase-07-web-game-table-and-results.md:151-152`). The cross-cutting constraint is "files ≤200 lines" (`plan.md:72`) and phase 7's own non-functional requirement repeats it ("every component ≤200 lines, with `table-screen.svelte` delegating to sub-components", `phase-07-web-game-table-and-results.md:35`) — but "delegating" here only means rendering child components, not delegating the state/ticker/tag-queue logic itself, none of which is named as a separate file. Phase 5 faced the identical problem (one class doing routing + lifecycle + persistence + view-building) and explicitly split it into `room-do.ts` / `room-do-actions.ts` / `room-do-view.ts` / `room-do-store.ts` (`phase-05-room-durable-object-realtime.md:131-135`) for exactly this reason.
- **Failure scenario:** Phase 7 is already the largest phase (6h, 12+ new files, `plan.md:67`); if `table-screen.svelte` exceeds 200 lines mid-implementation, there is no named overflow file (unlike Finding 5's at-least-named-if-undeclared `reducer-events.ts`), so the implementer either violates the line-limit success criterion or invents a split not reviewed here (e.g. where does the tag-queue's 1.6 s expiry timer live — in the component or a store?).
- **Evidence:** `phase-07-web-game-table-and-results.md:56-66`, `:151-152` vs `phase-05-room-durable-object-realtime.md:131-135`.
- **Suggested fix:** Pre-declare a `src/lib/table-state.svelte.ts` (mirroring `room.svelte.ts`'s pattern from phase 6) that owns `selected`, `tags`, `now`, and the derived combo/canPlay/remain, leaving `table-screen.svelte` to only wire the store and render children — the same split phase 5 already uses for its DO.
