# Red Team Review: Security Adversary — Sâm Lốc Online Plan

Reviewer role: security adversary / fact-checker. Scope: plan.md + phase-01..08, cross-checked against docs/game-rules.md, docs/tech-stack.md, docs/deployment.md, and the wireframes. All findings below are grep-verified against the actual plan text quoted inline.

## Finding 1: Registration is fully open to the public internet, defeating the "private group" trust model

- **Severity:** Critical
- **Location:** Phase 4, section "Route contracts", `phase-04-worker-auth-and-d1.md:84`; Phase 8, section "Security Considerations", `phase-08-deploy-docs-and-smoke-test.md:160,166-167`
- **Flaw:** `POST /api/register` (`phase-04-worker-auth-and-d1.md:84`) takes only `{ username, password }` — no invite code, admin approval, or allowlist. Every phase's threat model rests on "accounts belong to the friend group," but nothing in phases 1–8 enforces that. Phase 8 explicitly names the missing control and defers it: `phase-08-deploy-docs-and-smoke-test.md:166-167` — "Post-launch candidates, none committed: … a Cloudflare Access rule in front of `/api/register` to stop outside sign-ups." That means the plan ships to the public `workers.dev` URL (`docs/deployment.md:15`) with zero admission control at launch, by the plan's own admission.
- **Failure scenario:** Anyone who finds or guesses the `workers.dev` URL (no secrecy is claimed for it) registers an account in one `curl` call. They now hold a fully valid session cookie and can call every `/api/*` route and open `/ws/:code` for any room code they later obtain (shared casually over chat, shoulder-surfed, or brute-forced against the ~1e9 keyspace with no throttle — see Finding 3). The entire "opponents' hands never leave the server" guarantee (`plan.md:22-23`) is moot if an uninvited stranger can become a seated player.
- **Evidence:** `phase-04-worker-auth-and-d1.md:84`; `phase-05-room-durable-object-realtime.md:194-195` ("Anyone with a room code and an account can join; accepted for a private group, capped at `max_players`."); `phase-08-deploy-docs-and-smoke-test.md:160,166-167`.
- **Suggested fix:** Minimum viable gate consistent with YAGNI: a single shared invite/signup code (env var checked in `routes-auth.ts` register handler, no new schema) rejected with the existing Vietnamese error pattern. This is a few lines, not "a new auth system" — the phase-8 text frames the alternative as disproportionate, but a shared secret is not.

## Finding 2: No throttling on `/api/login` or `/api/register` enables unlimited credential stuffing / signup spam

- **Severity:** High
- **Location:** Phase 8, section "Security Considerations", `phase-08-deploy-docs-and-smoke-test.md:162`
- **Flaw:** `phase-08-deploy-docs-and-smoke-test.md:162` states outright: "Leave rate limiting out for now. Revisit only if `/api/login` sees unexpected traffic in the dashboard." Combined with Finding 1 (open registration, public URL) and the identical-error-message anti-enumeration control at `phase-04-worker-auth-and-d1.md:189` (which is good practice but does not slow down guessing), there is no per-IP or per-account attempt cap anywhere in phases 4, 5, or 8.
- **Failure scenario:** An outside attacker scripts unlimited password guesses against a known or enumerated username (usernames are `3-20` lowercase alnum, `phase-04-worker-auth-and-d1.md:38`, easy to guess for a "circle of ~10 friends" — first names). PBKDF2 at 100k iterations (`phase-04-worker-auth-and-d1.md:104`) slows a single guess but does not stop a distributed or patient attacker; there is no lockout, no CAPTCHA, no backoff. A hijacked friend's account lets the attacker see that friend's hand in an active room (breaking the core hidden-information guarantee) and impersonate them in chat-free but score-affecting gameplay.
- **Evidence:** `phase-08-deploy-docs-and-smoke-test.md:162`; risk table `phase-04-worker-auth-and-d1.md:179` only discusses PBKDF2 CPU budget, not brute-force resistance.
- **Suggested fix:** A minimal in-Worker fixed-window counter (KV or the existing `sessions` D1 table keyed by username+day, since D1 is already in the stack) capping failed logins to e.g. 10/hour is proportionate and small, not enterprise WAF-grade.

## Finding 3: No per-connection message-rate limit on the WebSocket lets one client burn the shared free-tier request quota for the whole app

- **Severity:** High
- **Location:** Phase 5, section "Connection flow and message handling", `phase-05-room-durable-object-realtime.md:90-102`; cross-checked against `docs/deployment.md:21`
- **Flaw:** The message switch (`phase-05-room-durable-object-realtime.md:92-101`) accepts `ready`, `leave`, `join`, `settings`, `declareSam`, `pass`, `play` at any rate — there is no debounce, cooldown, or per-socket message budget anywhere in phases 5–8 (confirmed absent by grep across all phase files). `phase-05-room-durable-object-realtime.md:102` states: "every accepted message ends with `snapshotAll()`" — i.e. every accepted message fans out one frame per connected socket. `docs/deployment.md:21` confirms: "WS messages count as requests when not hibernated," against a shared 100k Worker + 100k DO requests/day free-tier ceiling.
- **Failure scenario:** A single misbehaving or malicious client (does not even need to be an outsider — any of the ~10 friends' compromised or buggy client, or the account from Finding 1) opens a socket and fires thousands of trivially-valid messages per minute (e.g. toggling `ready`/`unready`, or `leave`+`join` cycles, both of which pass validation cheaply and each trigger a `snapshotAll()` fan-out to every seat). This exhausts the shared daily DO/Worker request budget in minutes, locking out all ~10 real players for the rest of the day — a concrete free-tier DoS the plan's own risk table (`phase-05-room-durable-object-realtime.md:181`) only models against *legitimate* traffic ("~200 frames/hand"), not an adversarial client.
- **Evidence:** `phase-05-room-durable-object-realtime.md:92-102`; `docs/deployment.md:21`; risk table `phase-05-room-durable-object-realtime.md:181` (no adversarial-rate scenario considered).
- **Suggested fix:** A cheap per-socket token bucket in `room-do.ts` (e.g. reject >20 messages/10s with a `{type:'error'}`, no disconnect needed) — a few lines in a file already owned by this phase.

## Finding 4: Unbounded, uncapped `POST /api/rooms` calls create Durable Objects that are never reclaimed

- **Severity:** Medium
- **Location:** Phase 4, section "Implementation Steps" step 9, `phase-04-worker-auth-and-d1.md:151-153`; Phase 5, `phase-05-room-durable-object-realtime.md:28`
- **Flaw:** `POST /api/rooms` (`phase-04-worker-auth-and-d1.md:89,151-153`) has no per-user or per-IP cap on how many rooms an authenticated account may create. Each call provisions a new `RoomDO` (via `env.ROOM.idFromName(code)` on first `/ws/:code` contact) with its own persistent SQLite storage that, per the plan, is never deleted — "an empty room closes" (`phase-05-room-durable-object-realtime.md:28`) describes only an in-memory `status` transition inside the DO; no implementation step in phase 4, 5, or 8 issues a `DurableObjectStub` delete or storage-clear call anywhere (confirmed absent by grep across all phase files).
- **Failure scenario:** Any authenticated account (including the outside account from Finding 1) scripts repeated `POST /api/rooms` calls. Each creates a permanent D1 `room_sessions` row and, on first WS contact, a permanent `RoomDO` with its own SQLite storage. Over the free tier's storage/object-count limits this is a slow-drip resource-exhaustion path with no mitigation in the plan; the phase-8 risk table (`phase-08-deploy-docs-and-smoke-test.md`) only discusses request-count limits during the smoke test, not sustained room-creation abuse.
- **Evidence:** `phase-04-worker-auth-and-d1.md:151-153` (no rate limit language); `phase-05-room-durable-object-realtime.md:28` (closes = status flag only, no storage teardown documented anywhere in the plan).
- **Suggested fix:** Cap rooms created per user per day in the existing `routes-rooms.ts` handler with a cheap `COUNT(*) FROM room_sessions WHERE host_user_id=? AND created_at > ?` check — no new infrastructure.

## Finding 5: `room_sessions.closed_at` is defined and read but never written, so finished rooms are reported open forever and their state is rejoinable indefinitely

- **Severity:** Medium
- **Location:** Phase 4, section "D1 schema" and route table, `phase-04-worker-auth-and-d1.md:57,90,94`; Phase 5, `phase-05-room-durable-object-realtime.md:28`
- **Flaw:** The schema comment at `phase-04-worker-auth-and-d1.md:57` reads "`closed_at INTEGER -- NULL while the room is open`," and `GET /api/rooms/:code` (`phase-04-worker-auth-and-d1.md:90`) and the `/api/sessions` query (`phase-04-worker-auth-and-d1.md:94`) both read `closed_at`. Grep across phases 4, 5, and 8 finds no implementation step, D1 write, or DO callback that ever sets `closed_at`. Phase 5's "an empty room closes" (`phase-05-room-durable-object-realtime.md:28`) is DO-internal `status` bookkeeping (`room-do.ts`/`room-do-actions.ts`, per `phase-05-room-durable-object-realtime.md:131-137`) with no described write-back to the D1 `room_sessions` row.
- **Failure scenario:** A finished/abandoned room's code always reports `closed: false` via `GET /api/rooms/:code`, and its `RoomDO` (with full seat list, totals, and — while `status='hand-end'` — the last hand's revealed cards per `phase-05-room-durable-object-realtime.md:125-127`) persists indefinitely and is rejoinable by anyone who later obtains that code (a code shared once in a chat and forgotten, then reused or leaked months later). This directly weakens the room-isolation boundary the plan otherwise relies on the code's secrecy for.
- **Evidence:** `phase-04-worker-auth-and-d1.md:57,90,94`; `phase-05-room-durable-object-realtime.md:28`; no counter-evidence of a D1 write found in any phase file (grep for `closed_at` returns only the three read/schema sites above).
- **Suggested fix:** When the DO transitions to empty (`endHand`/`leave` path emptying all seats), have it call back to `/api/rooms/:code/close` (or a direct `ctx.waitUntil(env.DB...)` update) to set `closed_at = now()`. This is a one-line addition to logic phase 5 already owns.

## Finding 6: `stake_per_la`, `max_players`, and `turn_seconds` set at `/api/rooms` creation can silently diverge from what the DO later enforces, with no reconciliation described

- **Severity:** Medium
- **Location:** Phase 5, section "Connection flow and message handling", `phase-05-room-durable-object-realtime.md:95`
- **Flaw:** `settings -> host only, status='waiting', validated by the phase-4 whitelist` (`phase-05-room-durable-object-realtime.md:95`) lets the host change `RoomSettings` live in the DO, but nothing in phase 4 or 5 writes the changed settings back to the D1 `room_sessions` row that `GET /api/rooms/:code` (`phase-04-worker-auth-and-d1.md:90`) and the WS-upgrade handshake (`phase-05-room-durable-object-realtime.md:83-85`, which reads `SELECT settings FROM room_sessions` to build the `x-max-players`/`x-turn-seconds`/`x-stake` headers) both rely on.
- **Failure scenario:** Host changes `stakePerLa` from 100 to 500 while waiting; the DO's live state and every already-connected socket reflect 500, but a new join (a reconnect, or a player who left and needs to re-authenticate the WS upgrade) re-derives its settings headers from the stale D1 row (100) via `routes-ws.ts` (`phase-05-room-durable-object-realtime.md:151-152`). Since `phase-05-room-durable-object-realtime.md:86` notes `ensureRoom(headers)` only seeds the row "on first contact," a returning player's stub call carries stale settings headers that the DO may or may not reconcile — the plan does not specify. This is a correctness/fairness gap (stake amounts are the entire scoring mechanism) rather than a confidentiality break, but it is a trust-boundary inconsistency between the two sources of truth the plan itself defines (D1 = "settings," DO = "authoritative state").
- **Evidence:** `phase-05-room-durable-object-realtime.md:83-86,95,151-152`; no D1 write-back for settings changes found in any phase file.
- **Suggested fix:** Either make the DO the sole source for settings on every WS upgrade (skip the D1 `SELECT settings` read after first contact and let the DO report its own current settings), or write settings changes back to D1 synchronously in the same handler that already does host-only validation.

**Status:** DONE
**Summary:** Six findings, all grep-verified against the plan text: one Critical (open registration undermines the entire "private group" trust model, and the plan's own phase 8 defers the fix post-launch), two High (no throttling on login/register enabling credential stuffing; no WebSocket message-rate limit enabling a single client to exhaust the shared free-tier request quota for all players), and three Medium (unbounded room creation with no DO cleanup; `closed_at` defined but never written, so finished rooms stay indefinitely rejoinable; room settings can diverge between D1 and the DO with no reconciliation path described). No fabricated mitigations were assumed present — each "missing control" claim was confirmed absent by grep across all phase files before being reported.
**Concerns/Blockers:** None blocking this review. Findings 1–3 are launch-blocking in my assessment even under the stated "private, no money, minimal scope" framing, because they don't add enterprise controls — they close gaps in the plan's own stated threat model (private group, hidden hands, free-tier viability). Findings 4–6 are pre-existing-debt-acceptable if the team explicitly signs off, but should not be silent gaps.
